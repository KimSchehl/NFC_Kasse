This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Is

**NFC-Kasse** is a cashless POS system for events. Guests receive NFC wristbands with a pre-loaded balance; staff scan wristbands on a tablet to deduct purchases. The system runs on a local LAN (no internet required at runtime).

- **Backend:** FastAPI + SQLite, running on a Windows thin client
- **Frontend:** Flutter tablet app (Android) + Flutter web build, deployed via ADB Wi-Fi / served by the backend
- **NFC Input:** Native `nfc_manager` on Android; USB HID keyboard emulation on desktop/web; battery-powered BLE reader (`nfc-ble-reader/`) on both Android and web
- **Language convention:** Code and DB identifiers in English; all user-facing text in German

Most files live under `NFC_Flutter_Project/`, with sibling hardware folders:

```
NFC_Kasse/
├── NFC_Flutter_Project/
│   ├── backend/              # Python FastAPI backend, Windows service, admin_cli.py
│   ├── nfc_kasse_app/        # Flutter POS app (Android + web build in backend/webapp)
│   ├── nfc_kasse_admin/      # Flutter Windows admin tool (service, Feste, config, bon layout, backups)
│   ├── license_tool/         # Licence keys for the Pager / Leaderboard add-ons

│   └── build_and_deploy.bat  # Build APK + web app, deploy to tablets / copy into backend/webapp

└── nfc-ble-reader_case/       # 3D-printed case + PCB fabrication files for the reader
```

**Ownership model (schema v3, see `NFC_Flutter_Project/docs/VERANSTALTER_PLAN.md`):** a **Veranstalter** (= `tenant`) owns users, rights, categories, articles and chips. An **event** (a Fest, or the permanent "Intern" event) owns only what happened during it — sales, top-ups, periods, pagers, print jobs — plus *which* of the tenant's categories/articles it shows (`event_category` / `event_product`). Several Veranstalter on one server are fully separate kassen; locally exactly one is active (`tenant.active`, chosen in the admin tool). The planned cloud version runs many tenants in one PostgreSQL — keep new SQL portable and always filter by the token user's `tenant_id`.

**Documentation map:** this file is the single developer reference; `NFC_Flutter_Project/README.md` lists where every other topic lives. The schema's source of truth is `backend/init_db.py` (+ `migrations.py`), the API's is the generated Swagger UI at `/docs`. Don't re-create hand-written schema/API/screen docs — they drifted and were removed.

## Commands

### Backend

```bash
# Windows — one-click (auto-installs Python, pip deps, creates DB if needed)
start_backend.bat

# Manual (any OS)
cd backend
pip install -r requirements.txt
python init_db.py          # first run only — creates kasse.db
SECRET_KEY=<hex> python -m uvicorn main:app --host 0.0.0.0 --port 8000 --reload
```

`config.env` (auto-generated by the bat script) provides `SECRET_KEY` and optionally `ALLOWED_ORIGINS`.

**After any schema change:** update both `init_db.py` (fresh databases) and `migrations.py` (existing installations, runs on every start, versioned via `PRAGMA user_version` / `db_backup.SCHEMA_VERSION`). For a throwaway dev DB, deleting `backend/kasse.db` and re-running `python init_db.py` is fine.

Interactive API docs: `http://localhost:8000/docs`

```bash
# Backend tests (isolated temp DB — safe to run anytime)
cd backend
pip install -r requirements-test.txt
pytest
pytest -v -k "test_book_same_product_twice"   # single test
```

### Flutter App

```bash
cd nfc_kasse_app
flutter pub get
flutter run                                    # requires connected device/emulator
flutter test                                   # unit tests, no device needed
flutter test test/providers/cart_notifier_test.dart   # single file
```

The server URL is entered on the login screen and stored via `AppStorage` (`lib/services/app_storage.dart`, SharedPreferences-backed); the constant in `lib/config/api_config.dart` is only the UI default. A release web build always uses its own page origin (it is served by the backend). On Android the login dropdown also lists servers found via mDNS/DNS-SD (`lib/services/server_discovery_service.dart`, `bonsoir`), which the Windows service announces as `_nfc-kasse._tcp` (`service_main._advertise`, `zeroconf`; not in uvicorn dev runs). This also holds auth tokens and every other piece of local app state — `FlutterSecureStorage` was deliberately dropped project-wide because its Web Crypto backing only works in secure contexts (HTTPS/localhost), and this app runs over plain HTTP on the LAN.

## Architecture

### Backend

**Entry point:** `main.py` — registers routers, configures CORS.

**Database access:** `database.py` provides `get_db(exclusive=False)` context manager. All booking and payout operations must use `get_db(exclusive=True)` to get a SQLite `BEGIN EXCLUSIVE` lock and prevent concurrent balance races.

**Auth pipeline:**
1. `dependencies.py` / `get_current_user()` — validates the JWT Bearer token on every request
2. `require_permission("permission.id")` — FastAPI `Depends` factory for endpoint-level permission checks
3. Refresh tokens are stored SHA-256 hashed in `refresh_token` table; on refresh the old token is revoked and a new pair is issued (token rotation)

**Routers and their core responsibilities:**

| Router | Endpoints | Key logic |
|---|---|---|
| `auth.py` | `/login`, `/refresh`, `/logout`, `/me` | JWT + refresh token lifecycle; `/me` returns full permission set + category access flags for the session |
| `products.py` | `/categories`, `/products` | Category list filtered by `user_category_access`; managers see all |
| `sales.py` | `/balance/{uid}`, `/` (POST booking), `/{id}/cancel` | Exclusive transaction; per-category `can_book` / `can_storno_*` checks |
| `topup.py` | `/topup`, `/payout` | Requires `guthaben.topup` / `guthaben.payout` global permission |
| `users.py` | `/users`, `/users/{id}/permissions`, `/users/{id}/categories`, `/permission-tree`, `/role-templates` | User CRUD + fine-grained permission + category-access assignment |
| `stats.py` | `/revenue`, `/transactions`, `/periods` | Revenue rollup, transaction history, Tagesabschluss (only while a fest runs) |

Further routers: `customers.py` (chip list/summary), `printer.py` (bon printing via `bon.drucken`, print-job queue worker), `pager.py`, `leaderboard.py` (TV page + SSE, no auth), `kiosk.py` (guest self-service), `display.py` (customer display via SSE), `help.py` (Notfall/WebSocket, `help.receive`), `logs.py` (client log ingest + viewer, `logs.*`), `preferences.py` (per-user UI prefs), `update.py` / `download.py` (APK self-update and download page). The full, current list with schemas is the Swagger UI at `/docs`.

Starting/ending a Fest, changing the running Fest's name/Pfand (`event-update`, live), Festvorlagen export/import, the accounting CSV export and Veranstalter management (`tenants`, `tenant-create` — password on stdin —, `tenant-activate`, `tenant-rename`, in `tenants.py`) are **not** HTTP endpoints: the admin tool (`nfc_kasse_admin/`, Windows, runs on the server) calls `NfcKasseBackend.exe <command>` → `admin_cli.py` → `event_lifecycle.py` / `tenants.py`, same as backups (`db_backup.py`). All Fest commands act on the active Veranstalter. No login there — whoever operates the server already controls service, config and backups. Every catalog write (article/category create/edit/delete/switch, `event-update`) calls `catalog.bump_revision()`; devices reload /me, categories and articles when `catalog_rev` in `/health` changes (`CatalogRevisionWatcher`). Devices notice a fest switch via `active_events` in their 10s `/health` poll (`ActiveEventWatcher` in the app's `providers.dart`). Every write endpoint calls `ensure_event_active()` (`dependencies.py`) first inside its exclusive transaction — the active event is resolved *before* the lock, so without it a write racing a switch would land in the just-ended fest. That check, and booking an article of another event, raise `EventChangedError` → 409 `{"code": "event_changed"}`, on which the app's `ApiClient` triggers an immediate reload.

### Permission Model

The permission tree is data (`permission_node`, seeded in `init_db.py` `seed_permissions()`, added to old DBs in `main.py` `_migrate()`); the user-facing explanation is `docs/anleitungen/Bedieneranleitung.md` §6. Rights belong to the user (and thus the tenant), not to a fest — neither table has an `event_id`; nothing is copied on a fest switch. Shared helpers (manager check, category flags, "switched on in this event" SQL) live in `backend/catalog.py`.

**Two layers:**

1. **Global permissions** (`user_permission` table) — coarse capabilities:
   - `guthaben.topup`, `guthaben.payout`
   - `categories.create`, `categories.edit`, `categories.deactivate`, `categories.delete`
   - `statistics.revenue`, `statistics.transactions`
   - `users.view`, `users.create`, `users.edit`, `users.deactivate`, `users.delete`, `users.manage_permissions`
   - `help.receive`, `bon.drucken`, `kiosk.access`, `logs.view`, `logs.configure`

2. **Per-category permissions** (`user_category_access` table) — 7 boolean columns:
   - `can_book`, `can_storno_5min`, `can_storno_unlimited`
   - `can_create_article`, `can_edit_article`, `can_deactivate_article`, `can_delete_article`

A category is listed for a user as soon as any of its 7 flags is set **and** it is switched on in the running event; booking needs `can_book`. `can_deactivate_article` also reveals inactive articles and allows switching an article on/off for the event (`PATCH /api/products/{id}/event-active`); `categories.deactivate` switches a category (`PATCH /api/products/categories/{id}/active`). `GET /api/products/categories?all=true` lists every tenant category with `active_in_event` (managers and `users.manage_permissions` only — the rights dialog uses it).

**Money rules in `sales.py` `create_booking()`** (on top of category access): a payout article (`is_payout`, must be alone in the cart) needs `guthaben.payout` and skips the `can_book` check; any article with a negative price that is neither `is_pfand` nor `is_payout` (= top-up article) needs `guthaben.topup`. Pfand articles need neither. `printer.py` `print_bon()` (cash sale) applies the same rules, including `can_book`. An option of an inactive base article and an article of a deleted category are not bookable. Payout sales cannot be cancelled. `/api/topup` accepts 0 < amount ≤ 1000 € (`schemas.MAX_TOPUP`).

**Manager bypass:** Any user with at least one of `categories.create / edit / deactivate / delete` is treated as a manager — they bypass all per-category checks (book, storno without time limit, article management) and see every category with full flags. Check is done with `_is_manager(db, user_id, event_id)` in `sales.py` (and `_user_can_manage_categories` in `products.py`); `/me` returns full flags for every category.

**Storno exclusivity (UI only):** `can_storno_5min` and `can_storno_unlimited` are mutually exclusive in the edit dialog — selecting one clears the other. The backend treats them as independent booleans (both are valid independently).

**Other rules:**
- `kiosk.access` only forces the kiosk screen for a *kiosk-only* account (`UserModel.isKioskOnly`: that one permission, no categories). The seeded admin deliberately does not get it.
- The app's "Benutzer" sidebar entry is gated by `users.manage_permissions`, not `users.view`.
- `users.py` `_blocks_last_manager()` refuses to deactivate/delete the last active holder of `users.manage_permissions`.
- Fest start (`event_lifecycle.start_event`) copies the source event's *selection* (`event_category`/`event_product`), optionally narrowed by `category_ids`; a preset is matched by name (missing categories/articles are created, existing ones are not overwritten); `reset_stock` sets the switched-on articles' stock to NULL. Booking or bon printing an article/category not switched on raises `EventChangedError(NOT_IN_EVENT)` → 409 `event_changed`.
- Login, `/refresh` and `get_current_user` only accept users of an active tenant — `tenant-activate` (only while the current tenant runs Intern) thereby logs every device out. Unauthenticated pages (leaderboard, `/health`) use `tenants.active_event(db)`.
- Licences (`licensing.py`, Ed25519, keys from `license_tool/`): `licensing.check()` returns valid/missing/invalid/wrong_feature/wrong_installation/expired (optional `valid_until` in the payload). The main licence (feature `kasse`, config `LICENSE_KEY`) is required to start the Windows service (`service_main._require_main_license`; dev runs via uvicorn are not gated); `pager`/`leaderboard` gate the add-ons in `config.py`. The admin tool's Lizenzen page uses `admin_cli.py license-check`.
- /me returns `can_manage_articles` (any article right in any category, or manager) so the Artikelverwaltung stays reachable when no category is switched on in the running event.
- Role templates (`role_template*`, `GET /api/users/role-templates`, `POST /api/users/{id}/apply-template/{tid}`) exist in the API but have no UI in the app.

### Flutter App

**State management (Riverpod):**

- `authProvider` (`AsyncNotifierProvider`) — auth lifecycle; on cold start silently restores session via `/me` before showing the login screen
- `cartProvider` (`NotifierProvider<CartNotifier, List<CartItem>>`) — in-memory cart; `addProduct` merges quantities
- `categoriesProvider` / `productsProvider` — `FutureProvider(.family)`; invalidated via `categoriesRefreshProvider` / `productsRefreshProvider` integer bump
- `currentScreenProvider` / `selectedCategoryProvider` / `editModeProvider` — navigation and POS UI state
- `bleReaderProvider` (`NotifierProvider<BleReaderNotifier, BleReaderState>`) — BLE NFC reader connection lifecycle; not `.autoDispose`, lives for the whole app session

All providers are defined in `lib/providers/providers.dart`.

**API client (`lib/services/api_client.dart`):**

Dio instance with a request interceptor that injects the Bearer token and a response interceptor that catches 401, calls `/refresh` once (shared `_refreshFuture` prevents concurrent refresh storms), updates stored tokens, and retries the original request.

**Responsive layout:**
- `≥ 600 px`: persistent `AppSidebar` + content area (tablet landscape)
- `< 600 px`: `Drawer` + full-screen content (phone)

**Edit dialogs (`lib/widgets/dialogs/`):**

- `edit_user_dialog.dart` — the most complex widget; renders a tri-state checkbox tree for both global permissions (`_PermissionGroup`) and per-category permissions (`_CategoryTreeTile`). The storno section uses a real `Radio` widget pair wrapped in `RadioGroup` (Flutter ≥ 3.32 API).
- `edit_product_dialog.dart` — article flags: Guthaben Aufladung (stored as negative price + `exclude_from_stats`), Pfand-Artikel (`is_pfand`), Auszahlungs-Artikel (`is_payout`), options (`group_id`), stock, default colour.
- `edit_category_dialog.dart` — rename + optional delete (requires `categories.delete` global permission).

**BLE NFC reader:**

Third UID input path alongside native NFC and USB HID (all three feed into `lib/widgets/nfc_input_field.dart`, which sets the field read-only while a BLE reader is connected so tapping it doesn't pop the on-screen keyboard). `BleReaderNotifier` (`lib/providers/providers.dart`) owns scanning, GATT connect, and the two characteristics exposed by `nfc-ble-reader/` firmware: a custom UID characteristic and the standard BLE Battery Service. The paired device is persisted via `AppStorage` (`storageProvider`) so it reconnects automatically on next app start — except on web, see below. Settings → "NFC-Lesegerät" tab (`_BleTab`/`_BleScanList` in `settings_screen.dart`) handles pairing/forgetting and shows live connection + battery status; the same status also appears as a small icon next to the server-connection indicator in `main_shell.dart`.

Two web-specific (`kIsWeb`) constraints, both browser limitations rather than app bugs:
- **No reconnect-by-ID.** Web Bluetooth only ever grants a connectable device handle through its own `requestDevice()` picker UI, freshly per page load — a remembered device ID alone can never resolve. `_restoreSavedDevice()` and the Settings "Verbinden" action branch on `kIsWeb` accordingly: show "paired but disconnected" / trigger a new scan (which re-opens the browser's picker) instead of attempting a doomed direct connect.
- **No external-disconnect notification.** `flutter_blue_plus_web` only reports a disconnect the app itself triggers, never one caused by the peripheral (powered off, out of range) — so the UI would otherwise show "connected" forever. Worked around with a *passive* liveness check (`_startWebHealthCheck`): compares time since the firmware's last Battery Service notify (sent every ~60s) against a threshold, rather than actively probing the GATT link. This is deliberate — every flutter_blue_plus operation (read/write/connect/discoverServices) shares one mutex per device that's only released once the underlying browser call actually settles; an active probe that hangs instead of rejecting (which is exactly what happens when the link dies quietly) would permanently deadlock all further operations on that device, including the reconnect attempt itself.

## Database Schema Highlights

Full schema with per-column comments: `backend/init_db.py`. Key tables and non-obvious design decisions:

- **`tenant`** — the Veranstalter; `active = 1` for the one in use locally. Each has its own Intern event and BAR chip (`tenants.ensure_bar_chips`).
- **`event`** — exactly one active per tenant. `is_intern = 1` marks the permanent "Intern" event the kasse runs on between fests; fests carry their own `name`/`chip_deposit` (no config.env setting any more), `started_at`/`ended_at`.
- **`category`** (`tenant_id`) / **`product`** — owned by the tenant; `event_category(event_id, category_id)` and `event_product(event_id, product_id)` say what an event shows. `event_product` holds base articles only — an option follows its base via `COALESCE(p.group_id, p.id)` (`catalog.PRODUCT_IN_EVENT_SQL`). `product.active` is the global grey-out ("ausverkauft"), independent of the event selection; stock belongs to the article.
- **`sale`** — append-only; cancellation sets `cancelled = 1` (never deleted). `price_at_sale` snapshots the price, `points` the leaderboard points (0 at Intern).
- **`product`** — `price` is `REAL` in euros; negative prices are credits (top-ups or "Pfand −"). `is_payout` articles pay out the whole balance plus the chip's `deposit_paid`; `is_pfand` articles need no top-up right and never count as revenue; `group_id` makes a row an option of a base article (options share the base's stock/points/pager flag).
- **`customer`** — tenant-wide, balance survives fest switches. `is_available = 1` means the chip is free (never issued or paid out) and is treated as a new customer on its next booking; `deposit_paid` stores the Pfand actually taken so payout refunds exactly that.
- **`user_category_access`** — one row per (user, category) with 7 boolean columns; **`user_permission`** — one row per (user, permission).
- **Schema versions** — `db_backup.SCHEMA_VERSION = 3`. `migrations.migrate_v3()` upgrades v2 databases with its own connection (foreign keys off, table rebuilds, backup `vor-update_*` first): same-named categories per tenant and same-named articles per category from different events are merged (the running event's row wins), references and the app's layout/colour preference keys are remapped. The frozen v2 schema for tests is `backend/tests/legacy_init_db_v2.py`.
- **`permission_node`** — the permission tree is data-driven (seeded in `init_db.py`), not hardcoded in router logic.
- **`leaderboard_entry`** — per-event opt-in; points are summed from `sale.points` of the running event.
